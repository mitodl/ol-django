### Added

- `MITOL_APIGATEWAY_ADOPT_UNLINKED_USER_BY` lets the backend adopt a pre-gateway account that has no lookup-field value yet, matching it on a second field (typically `email`), instead of creating a duplicate on its owner's first login through the gateway. "No value yet" covers both an empty string and NULL, since apps differ on which they store. Defaults to `None` (off).

### Fixed

- `ApisixRemoteUserBackend.lookup_field` now reads `MITOL_APIGATEWAY_USER_LOOKUP_FIELD` instead of hardcoding `global_id`. The setting shipped but was never read.
- `ApisixUserMiddleware.process_request` compares the already-authenticated user on the gateway lookup field rather than `USERNAME_FIELD`. Where an app's `USERNAME_FIELD` is not the lookup field, `RemoteUserMiddleware`'s own comparison never matched, so every request logged the session out and re-authenticated.
- `configure_user` writes the user row (and any `additional_models` row) only when a mapped value actually differs from what is stored. It ran on every authenticated request and saved unconditionally.
- An ambiguous remote identity is now refused explicitly, with a log line naming the lookup field and value, rather than surfacing as a generic "Unable to authenticate api gateway user".
- A mapped name that is not a concrete model field no longer breaks the save. This was masked before by the unconditional `user.save()`.
- `RemoteUserCustomFieldBackend.aauthenticate` no longer fails on Django below 5.2. It called `self.aconfigure_user`, which `RemoteUserBackend` only gained in 5.2 while this package declares `django>=3.0` — an `AttributeError` on 4.2/5.0/5.1. It now goes through a shim, which is also load-bearing on 5.2 itself: Django's `aconfigure_user` passes `created` positionally, and `ApisixRemoteUserBackend.configure_user` declares it keyword-only. The shim is marked for removal once the Django floor reaches 5.2 and that signature is relaxed. Nothing had exercised this path, because the shipped backend overrides `aauthenticate`; it is covered now.
- The adoption filter no longer compares a non-textual lookup field against `""`. `lookup_field` is configurable, and a UUID or integer column raises while the query is built, which `authenticate()`'s blanket except would turn into a rejected login for every user.
- The ambiguous-identity log names the adoption field when adoption is what collided, instead of attributing every collision to the lookup field.
- Adoption claims the row with a conditional update rather than a blind save. Two identities carrying the same adoption value both select the one unlinked row; a save let the second overwrite the first's lookup id while both requests returned that same account. Re-stating the unset predicate in the `UPDATE` makes the claim atomic, so the loser matches nothing, re-resolves once, and creates its own user instead.
